We use the notation and the line numbers of the page. All secrets come from HKDF-Extract, HKDF-Expand-Label and Derive-Secret, which are deterministic functions of their inputs. We write $\mathrm{DS}(S, \ell, T)$ for Derive-Secret with the secret $S$, the label $\ell$ and the transcript $T$, so that $\mathrm{DS}(S, \ell, T) = \mathrm{HKDF\text{-}Expand\text{-}Label}(S, \ell, H(T), L)$ with $L$ the hash length.

**Lemma 1 (the schedule is a function of three inputs).** Every secret and key of one handshake is a deterministic function of the PSK (or the zero string when there is none), the shared Diffie-Hellman value $Z$, and the handshake messages.

*Proof.* The early secret is $ES = \mathrm{Extract}(0, PSK)$. The handshake secret is $HS = \mathrm{Extract}(\mathrm{DS}(ES, \text{derived}, \varepsilon), Z)$, and the master secret is $MS = \mathrm{Extract}(\mathrm{DS}(HS, \text{derived}, \varepsilon), 0)$. Each traffic secret is $\mathrm{DS}$ of $ES$, $HS$ or $MS$ with a fixed label and a prefix of the messages. The traffic keys, the Finished keys, the binder and the resumption PSK are Expand-Label of these secrets with fixed labels and contexts. Each step is a composition of deterministic functions. $\square$

**Lemma 2 (the shared value).** If the client sends $g_x = X25519(x, 9)$ in line L1 and receives $g_y = X25519(y, 9)$ in the ServerHello, then $X25519(x, g_y) = X25519(y, g_x)$.

*Proof.* X25519 computes the $u$-coordinate of $[k]P$ on Curve25519, with $k$ the clamped scalar. Clamping sets the low three bits of $k$ to zero, so $k$ is a multiple of the cofactor 8, and both sides equal the $u$-coordinate of $[k_x k_y] B$ with $B$ the base point, because scalar multiplication on a group is commutative: $[k_x]([k_y] B) = [k_x k_y] B = [k_y]([k_x] B)$. The Montgomery ladder computes $[k]P$ from the $u$-coordinate of $P$ alone, because the $u$-coordinate of $[k]P$ is the same for $P$ and $-P$. $\square$

**Theorem 3 (correctness).** Suppose that the client and the server follow lines L1 to L14, that no message is changed in transit, that the server's signing key is the key the client trusts for the server's name, and, in a resumption, that both hold the same PSK for the ticket. Then every check passes, and the two sides hold equal handshake, master, application, exporter and resumption secrets.

*Proof.* Both sides see the same messages in the same order, so their transcripts are equal at every point. In a resumption the client computes the binder in line L1 from the PSK and the transcript of the ClientHello without the binder; the server computes the same value in line L3 from the same PSK and the same bytes, so the check passes. By Lemma 2 both sides compute the same $Z$ in lines L5 and L10. By Lemma 1 they then compute the same $HS$, the same handshake traffic secrets, and the same record keys, so each record of the server's flight decrypts correctly under the study AEAD. In a full handshake, the client checks that the certificate names the server and carries the trusted key, which holds by assumption, and checks the signature in line L11 on the content built from the same transcript prefix that the server signed in line L7; Ed25519 verification accepts every honestly made signature. The server's Finished is the HMAC under $\mathrm{finished\_key}(s\_hs)$ of the transcript through CertificateVerify, which the client recomputes from equal inputs in line L12. In the same way the server's check of the client Finished in line L14 passes. Finally, both sides derive $MS$, the application secrets and the resumption secret from equal inputs by Lemma 1. $\square$

**Theorem 4 (a changed message breaks agreement).** Suppose that the attacker changes, adds or drops a handshake message, and that the client and the server both still complete the handshake. Then the attacker can compute a valid HMAC under a Finished key that it does not know, or a valid Ed25519 signature for a key that it does not hold, or the two sides derived different traffic keys and the first protected record fails.

*Proof.* Let $T_c$ and $T_s$ be the transcripts of the client and the server through the server's Finished, and suppose $T_c \ne T_s$. If the changed message is the ServerHello or the ClientHello, the two sides compute the handshake traffic secrets from different transcripts, and so (except with the probability of a hash collision) from different inputs to HKDF. If the server's flight decrypts at the client, the attacker made a record under a key it was not given, which is a forgery against the AEAD. Otherwise the server's records decrypt, so the keys agree, and the client accepts the server's Finished on $T_c$. The server made its Finished on $T_s \ne T_c$, so the value that the client accepts was not made by the server: it is an HMAC forgery under $\mathrm{finished\_key}(s\_hs)$. In a full handshake, the CertificateVerify signature also covers the transcript, so accepting it on $T_c$ needs a signature that the server did not make. $\square$

Theorem 4 is a reduction outline: it shows which primitive the attacker must break. The full proof of key secrecy, with the multi-stage key exchange model and the exact bounds, is in Dowling, Fischlin, Günther and Stebila (J. Cryptology 2021); the symbolic proof of all modes is in Cremers et al. (CCS 2017).

**Theorem 5 (single-use tickets stop 0-RTT replay at one server).** If the server runs with single-use tickets, it acts on at most one flight of early data for each ticket that it issued.

*Proof.* The server acts on early data only after line L3 found the ticket's identity in its table and the binder check passed. In the same step, before it reads the early data, it deletes the identity from the table. A later ClientHello with the same identity, whether a copy made by an attacker or a new one, finds no entry, so the server falls back to a full handshake without early data. Hence each identity leads to at most one accepted flight. $\square$

The claim holds for one server with one table. A deployment with many servers that do not share the table can accept the same flight once at each server. RFC 8446 Section 8 therefore asks for a shared or partitioned record of the used tickets or ClientHellos, together with a time window. $\blacksquare$
