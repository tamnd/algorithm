Pratt parsing, or top-down operator precedence, parses expressions with prefix, infix and postfix operators by giving each operator a number, its *binding power*, and letting the stronger binding win. It is a [recursive descent](/recursive-descent-parsing/) procedure EXPR(ρ) that reads one operand and then keeps absorbing operators while their left binding power exceeds ρ. One short loop replaces the chain of one procedure per precedence level, the parser runs in $\Theta(n)$ time for $n$ tokens, and new operators are added by adding rows to a table. Vaughan Pratt described it in 1973; it is the expression parser of many hand-written compilers and interpreters.

## In plain words

In `a + b * c`, the `b` sits between two operators, and both want it as an operand. The times sign pulls harder, so `b` goes with it. A Pratt parser gives every operator a pulling strength and lets each operand go to the stronger side.

The parser reads an operand, then looks at the next operator. If that operator pulls harder than whatever is waiting on the left, it takes the operand built so far as its left side and calls the parser again for its right side. Otherwise it hands what it has back to the waiting operator. For left grouping, as in `a - b - c`, an equal operator does not steal the operand. Parentheses restart the strength at zero, and a minus sign in front reads its operand with its own strength.

## The problem

The input is a sequence of $n$ tokens: operands, the parentheses `(` and `)`, and operators. Each operator is described by integers in a table:

- a **prefix** operator $t$ has a right binding power $\text{rbp}(t) \ge 0$, the strength with which it holds its operand;
- an **infix** operator $o$ has a left binding power $\text{lbp}(o) \ge 1$ and a right binding power $\text{rbp}(o) \ge 0$; the usual choice is $\text{rbp}(o) = \text{lbp}(o)$ for left associativity and $\text{rbp}(o) = \text{lbp}(o) - 1$ for right associativity;
- a **postfix** operator $o$ has $\text{lbp}(o) \ge 1$.

A token may be both prefix and infix, like `-`, but not both infix and postfix. Every other token, the end marker $\$$ and `)` have $\text{lbp} = 0$. The input is *well formed* if it is generated by the ambiguous grammar

$$E \to \text{id} \mid (\,E\,) \mid p\, E \mid E\, q \mid E\, o\, E$$

for prefix $p$, postfix $q$ and infix $o$ (we use the notation of the [context-free grammar](/context-free-grammar/) page: productions $A \to \alpha \mid \beta$, $\varepsilon$ for the empty string, $S$ for the start symbol, here $E$, $n$ for the input length and $|G|$ for the grammar size). The output is the [expression tree](/expression-tree/) of the input selected by the binding powers, defined in the Correctness section, or an error if the input is not well formed.

## The algorithm

```pseudo id=main
PARSE(tokens)
L1  pos ← 1;  t ← EXPR(0)
L2  if token[pos] ≠ $ then error
L3  return t

EXPR(ρ)
L4  t ← token[pos];  pos ← pos + 1
L5  if t is an operand then left ← leaf(t)                       ▷ the nud of an operand
L6  else if t = "(" then left ← EXPR(0);  expect ")" and advance
L7  else if t is a prefix operator then left ← node(t, EXPR(rbp(t)))
L8  else error                                                   ▷ an operand was expected
L9  while lbp(token[pos]) > ρ do
L10     o ← token[pos];  pos ← pos + 1                           ▷ the led of o
L11     if o is a postfix operator then left ← node(o, left)
L12     else left ← node(o, left, EXPR(rbp(o)))                  ▷ o is infix
L13 return left
```

Pratt's paper attaches to each token two pieces of code: the *nud* (null denotation), run when the token starts an expression (lines L5 to L7), and the *led* (left denotation), run when it follows a complete left operand (lines L11 and L12). The table form above covers the common operators. The code form allows anything else that starts with a token: a function call `f(x, y)` is a led of `(` with a high lbp, indexing `a[i]` a led of `[`, the conditional `c ? x : y` a led of `?` that calls EXPR(0), expects `:`, and calls EXPR again.

The only state is pos. The implementation of this page runs EXPR as a Python generator on an explicit stack, so deep nesting does not hit the recursion limit.

## Example

Take $\text{lbp} = \text{rbp} = 10$ for `+` and `-`, $20$ for `*` and `/`, $\text{lbp} = 30$ and $\text{rbp} = 29$ for the right-associative `^`, prefix `-` with $\text{rbp} = 25$, and postfix `!` with $\text{lbp} = 40$. The input is `- a ^ b * c + d !`:

```
EXPR(0) reads -                       prefix: operand is EXPR(25)
  EXPR(25) reads a
    lbp(^) = 30 > 25: take ^          right operand is EXPR(29)
    EXPR(29) reads b
      stop at *, lbp 20 <= 29         return b
    stop at *, lbp 20 <= 25           return (a ^ b)
  lbp(*) = 20 > 0: take *             left is (-(a ^ b)), right operand is EXPR(20)
  EXPR(20) reads c
    stop at +, lbp 10 <= 20           return c
  lbp(+) = 10 > 0: take +             right operand is EXPR(10)
  EXPR(10) reads d
    lbp(!) = 40 > 10: take !          left becomes (d!)
    stop at $, lbp 0 <= 10            return (d!)
  stop at $, lbp 0 <= 0               return (((-(a ^ b)) * c) + (d!))
```

The prefix minus binds less tightly than `^` and more tightly than `*`, so it takes $a \,\hat{}\, b$ but not the product. With the same table, `a - b - c` gives $(a - b) - c$, because in EXPR(10) for the right operand of the first `-` the second `-` has $\text{lbp} = 10 \le 10$; and `a ^ b ^ c` gives $a \,\hat{}\, (b \,\hat{}\, c)$, because in EXPR(29) the second `^` has $\text{lbp} = 30 > 29$. A loose prefix operator such as `not` with $\text{rbp} = 5$, below `and` at 10 and `==` at 20, reads `not a == b and c` as $\text{not}\,((a == b) \text{ and } c)$.

## Correctness

The grammar of the problem is ambiguous, and the binding powers choose one tree. Call a tree of the grammar *valid* if:

- **(A)** for every node with an operator $o$ that takes a left operand (infix or postfix), $\text{lbp}(o) \le \text{rbp}(X)$ for every node $X$ on the right spine of the left operand (the chain of infix and prefix nodes reached by repeatedly taking the right operand);
- **(B)** for every node with a right operand (infix or prefix) of binding power $\rho$, $\text{lbp}(Y) > \rho$ for every node $Y$ on the left spine of that operand that takes a left operand (the chain of infix and postfix nodes reached by repeatedly taking the left operand).

Parentheses end both spines. Condition (B) says that EXPR(ρ) only attaches operators stronger than ρ; condition (A) says that an operator was not absorbed into the right side of an operator on its left.

**Claim.** PARSE returns a tree if and only if the input is well formed, and then the returned tree is the unique valid tree of the input.

The proof has three parts ([full proof](proofs/correctness.md)). First, each call EXPR(ρ) that returns, stopping at a token $t$, gives a valid tree whose right spine nodes all have $\text{rbp} \ge \text{lbp}(t)$, and $\text{lbp}(t) \le \rho$; this gives (A) and (B) for the trees it builds. Second, by induction on the size of a valid tree $T$ of the tokens from position $p$, if the token after it has $\text{lbp}$ at most $\rho$ and at most the rbp of each node on the right spine of $T$, then EXPR(ρ) started at $p$ returns exactly $T$: it must read the bottom of the left spine of $T$ first, and condition (B) and the right spine bound decide each step of the loop as $T$ does. So there is at most one valid tree. Third, at any moment all pending calls wait in the state "after an operand", and the top call EXPR(0) absorbs every infix or postfix operator, so the parser fails only where the regular structure of a well-formed token sequence fails. The tests compare the parser with an enumeration of all trees of the ambiguous grammar, filtered by (A) and (B), on 7500 random tables and inputs with ties of binding powers, and on all 19608 strings of up to 5 tokens over a fixed table.

## Complexity

Every call of EXPR reads one token at line L4, and every round of the loop reads one at line L10. Each token is read once, so there are at most $n + 1$ calls and $n$ rounds, each with $O(1)$ work outside the calls: the time is $\Theta(n)$ on well-formed input, and $\Theta(1)$ in the best case, an error on the first token. The nesting of calls is at most $n + 1$ deep, for example $n$ prefix minus signs or a chain of right-associative operators, and the tree has $O(n)$ nodes, so the extra space is $O(n)$.

## Properties

- **Deterministic and one pass.** Each token is looked at a constant number of times; the only lookahead is one token in line L9.
- **Online.** An error is reported at the first token that cannot continue a well-formed prefix.
- **Recursive.** The pending operators live on the call stack, where the [shunting-yard algorithm](/shunting-yard-algorithm/) keeps them on an explicit operator stack. For infix operators with $\text{lbp} = 10 \times$ the precedence level and $\text{rbp} = \text{lbp}$ or $\text{lbp} - 1$ by associativity, the two produce the same tree.
- **Table driven and extensible.** Adding an operator adds one entry, with no new grammar levels; this is why parsers for languages with user-defined operators use it.

## Variants and improvements

- **Precedence climbing.** The same loop, written with precedence levels and associativity flags instead of two binding powers, is often called precedence climbing; it is Pratt parsing with $\text{rbp}(o) = \text{lbp}(o)$ or $\text{lbp}(o) - 1$.
- **Binding power pairs.** Some presentations give each infix operator a pair $(l, r)$ with $l < r$ for left and $l > r$ for right associativity, and stop the loop when $l < \rho$. This is the same algorithm with the comparison shifted.
- **Mixfix.** Leds that read more than one operand, such as the conditional operator or a call with an argument list, extend the method beyond binary operators while keeping the loop.
- **Statements.** Crockford's version gives statement keywords their own "std" code and parses a whole language with the same table.

## When to use it

Use a Pratt parser for the expression part of a hand-written [recursive descent](/recursive-descent-parsing/) parser, especially when there are many precedence levels, prefix and postfix operators, or operators defined by the user. Use the [shunting-yard algorithm](/shunting-yard-algorithm/) when you want postfix output with no recursion. Use a parser generator with precedence declarations when the whole grammar is generated anyway ([LALR parsing](/lalr-parsing/) with the precedence rules of [yacc](/yacc/)).

## Pitfalls

- **Strict versus loose comparison.** Line L9 uses $>$. With $\ge$ and $\text{rbp} = \text{lbp}$, the operators group to the right: `a - b - c` becomes $a - (b - c)$.
- **Right associativity off by one.** With integer powers, $\text{rbp} = \text{lbp} - 1$ must still be above the lbp of every weaker operator; leave gaps between levels (10, 20, 30) so that the minus one does not fall onto another level.
- **Zero lbp for closers.** Tokens that end an expression, such as `)`, `]`, `,` and $\$$, must have $\text{lbp} = 0$, or the loop tries to use them as operators.
- **One token, two roles.** A token like `-` has both a nud and a led. The parser chooses by position, never by the token alone; a table that makes a token both infix and postfix is ambiguous for the loop.
- **Prefix power is not precedence level.** A prefix operator with a low rbp swallows the operators after it: `not a == b` is $\text{not}\,(a == b)$. That is usually intended for `not` and wrong for a unary minus.

## History

Vaughan Pratt presented top-down operator precedence at the first POPL symposium in 1973, as a way to give each token its own code (nud and led) and binding power rather than writing a grammar with one rule per level. The method stayed little known for decades, and it became popular after Douglas Crockford used it for a JavaScript parser in the 2007 book Beautiful Code. It is the expression parser of many hand-written front ends and of tutorials such as Robert Nystrom's Crafting Interpreters.
