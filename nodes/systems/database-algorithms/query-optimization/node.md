Query optimization is the problem of turning a declarative query, such as an SQL statement, into an execution plan that computes the same answer at the least cost. A query names what to compute, not how; the same result can be computed by many [query plans](/query-plan/), which differ in the order of joins, the join algorithms, the use of indexes and the place of selections, and their costs can differ by orders of magnitude. An optimizer has three parts (Chaudhuri 1998): a *search space* of equivalent plans, generated by algebraic rewrite rules; a [cost model](/cost-model/) with [cardinality estimates](/cardinality-estimation/); and a *search strategy* such as the [Selinger dynamic program](/selinger-join-enumeration/). The exact problem is hard in several ways: [join ordering](/join-ordering/) alone is NP-hard, and the equivalence of general relational queries is undecidable, so optimizers search a space defined by rules and minimize an estimate.

## In plain words

When you ask a database a question, you say what you want, not how to get it. The database must find the steps. There are many ways to get the same answer. It can filter rows early or late. It can join the tables in many orders. It can read a whole table or use an index.

Some ways take a second, and some take hours. The optimizer is the part of the database that picks the way. It first changes the question into forms that are surely the same, such as moving a filter earlier. Then it estimates how many rows each step will make and what each step will cost, and it picks the plan with the least total cost. All this must happen fast, before the query runs, and with only estimates of the data.

## Definition

**Input.**

- A query $Q$, given as a [relational algebra](/relational-algebra/) expression, with bag semantics for SQL.
- A database schema with the available access paths (indexes, sort orders, [materialized views](/materialized-view/)).
- Statistics about the data, such as table sizes, numbers of distinct values and [histograms](/histogram/).
- A cost model $C$.

**Output.** A physical plan $P$ such that $P(D) = Q(D)$ for every database $D$ of the schema, with the least estimated cost $C(P)$ among the plans in the search space.

The *search space* is the set of plans that the optimizer can reach from $Q$ with its rules: logical rewrites that preserve the result on every database (such as [predicate pushdown](/predicate-pushdown/), join commutativity and associativity, and the unnesting of subqueries) and implementation rules that choose a physical operator for each logical one. The optimum is defined relative to this space and to the estimates; the true fastest plan may lie outside it, or may look worse under wrong estimates.

## Variants

- **Rule-based (heuristic) optimization.** Apply fixed rules, such as "push selections down" and "join the smallest tables first", without costs. Early systems and the first phase of most current optimizers work this way.
- **Cost-based optimization.** Enumerate alternatives and compare their estimated costs: the System R approach.
- **Plan space.** Left-deep plans only (System R), bushy plans, with or without cross products; see [join ordering](/join-ordering/).
- **Objective.** Total work, response time (for parallel plans), time to the first row (for interactive queries and LIMIT), or several objectives at once.
- **Parametric and robust optimization.** Choose plans for queries whose parameters or statistics are unknown at compile time, or prefer plans whose cost is less sensitive to estimation errors.
- **Adaptive query processing.** Change the plan during execution when observed sizes differ from the estimates.
- **Multi-query optimization.** Share common subexpressions among several queries.

## Examples

Let `Emp(eno, name, dno)` have 10 000 tuples on 1000 pages, with 100 employees per department, and let `Dept(dno, city)` have 100 tuples on 10 pages, 5 of them in Oslo. The query is

```
SELECT e.name FROM Emp e, Dept d WHERE e.dno = d.dno AND d.city = 'Oslo'
```

Its direct translation is $\pi_{\text{name}}(\sigma_{\text{dno}=\text{dno} \wedge \text{city} = \text{Oslo}}(\text{Emp} \times \text{Dept}))$. The plans, with page reads as the cost:

| plan | what it does | page reads |
|---|---|---|
| product, then filter | page nested loop over Emp and Dept, $10^6$ pairs tested | $1000 + 1000 \cdot 10 = 11\,000$ |
| push the selection, then join | scan Dept and keep its 5 Oslo tuples in memory, scan Emp once | $10 + 1000 = 1010$ |
| index nested loop, index on `Emp.dno` not clustered | for each of 5 departments, 2 index pages and 100 data pages | $10 + 5 \cdot (2 + 100) = 520$ |
| index nested loop, clustered index on `Emp.dno` | for each of 5 departments, 2 index pages and 10 data pages | $10 + 5 \cdot (2 + 10) = 70$ |

The first step is a logical rewrite that is always valid: [predicate pushdown](/predicate-pushdown/) moves `city = 'Oslo'` onto Dept and turns the product and the equality into a join. The rest is a cost-based choice, which depends on the estimate that only 5 departments qualify. If 90 departments were in Oslo, the index plan without clustering would cost $10 + 90 \cdot 102 = 9190$, and the scan of Emp (1010) would win. This is why cost-based optimization needs [selectivity](/selectivity/) estimates.

## Known algorithms

- **Rewrite rules.** A first phase applies rewrites that are almost always good: [predicate pushdown](/predicate-pushdown/), projection pushdown, view merging, and the unnesting of correlated subqueries into joins. For recursive queries, [magic sets](/magic-sets/) rewrite the program so that it computes only the facts relevant to the query.
- **Bottom-up dynamic programming.** The [System R enumeration](/selinger-join-enumeration/) builds the best plans for larger and larger sets of relations, with interesting orders. DPccp enumerates only connected subgraphs.
- **Top-down search with memoization.** The Volcano optimizer generator and the Cascades framework (Graefe 1995) start from the whole query, apply transformation rules to generate equivalent expressions, store them in a *memo* that groups equivalent subexpressions, and prune with cost bounds. SQL Server and several other systems use this design.
- **Heuristics and randomized search** for very large queries: greedy join ordering, iterative improvement, simulated annealing, genetic search (PostgreSQL's GEQO).
- **IKKBZ** for tree queries with ASI costs, in polynomial time; see [join ordering](/join-ordering/).
- **Using materialized views.** View matching rewrites parts of the query to read [materialized views](/materialized-view/), and the optimizer keeps the rewriting when it is cheaper.

## Bounds

- **Equivalence is undecidable in general.** Equivalence of relational algebra queries (first-order queries) is undecidable, by Trakhtenbrot's theorem, so no optimizer can search the space of all equivalent queries. For conjunctive queries, equivalence and [containment](/query-containment-problem/) are NP-complete by the [Chandra and Merlin theorem](/chandra-merlin-theorem/).
- **Join ordering is NP-hard** for general query graphs and common cost functions, so finding the optimal plan, even within a fixed rule-generated space, is NP-hard. The exact DP takes time exponential in the number of relations.
- **Estimates limit quality.** The optimum is computed for estimated sizes. Ioannidis and Christodoulakis (1991) showed that errors in size estimates grow exponentially with the number of joins, and Leis et al. (2015) found on real data that cardinality errors, more than the cost model or the search, cause bad plans.

## Reductions

- **Join ordering** is the core subproblem: an optimizer that can order joins and pick join methods well solves most of the problem for select-project-join queries.
- **Query equivalence** reduces to two containment tests ($Q_1 \subseteq Q_2$ and $Q_2 \subseteq Q_1$), so rewrites that are not covered by fixed rules need a containment test; see the [query containment problem](/query-containment-problem/).
- **Answering queries using views** is query optimization in which some inputs are [materialized views](/materialized-view/).
- **Physical design** problems, such as [index selection](/index-selection/) and [view selection](/view-selection/), call the optimizer as a subroutine to estimate the cost of a workload under a hypothetical design.

## Applications

Every relational database system has a query optimizer, and the same ideas appear in systems that are not relational: big data engines (Spark SQL's Catalyst optimizer), streaming systems, graph and SPARQL engines, and dataframe libraries that build a lazy plan and optimize it before running it. The [iterator model](/iterator-model/) or a vectorized or compiled engine then runs the chosen plan.
